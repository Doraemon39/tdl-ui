# 0.23.4 恢复启动性能修复

## 原因

恢复请求已进入后端，暂停/运行状态也能正确切换。延迟来自已完成断点的清单补记逻辑：它在判断清单是否已包含相同完成记录之前，逐个重读文件计算 SHA-256。媒体数量多或文件较大时，这段检查发生在新的文件下载之前，没有界面阶段提示，因此看起来像恢复无反应；再次暂停、恢复还会重做这一轮检查。

## 修改

- 对已经登记完成的断点，先以来源、消息、媒体身份、原名、大小、时间、保存名与摘要查询清单。对应记录已完整时直接沿用断点，不重复读取媒体内容或追加同一记录。
- 普通新任务的本地匹配仍需验证摘要；缺失或不一致的完成清单也仍先验证文件再补记，不把这个优化用于未经确认的本地文件。
- 自动清单增加只打开已有文件的路径；恢复检查不创建空清单，不消耗全局导入清单缓存。
- 摘要读取支持上下文取消，迭代器在连续跳过时也检查取消。
- 任务视图与任务页增加运行阶段提示；文件开始下载后清除阶段提示，任务结束也清除。

## 回归范围

新增回归在修改前复现已存在完整清单记录却仍重复验证和补记的路径；修改后覆盖导入清单、自动清单重启、缺失或过期记录补记、来源隔离、取消与阶段状态。保留此前暂停后恢复、错误状态恢复及进度保留测试。

Go 构建、全量测试、静态检查、前端类型检查/生产构建、8 项前端回归测试及 Windows amd64 Wails 生产构建通过。合成数据界面确认任务页阶段提示可见，控制台无错误或警告。

此次诊断只读运行程序的日志、任务库及清单元数据，没有重启客户端或修改用户的任务、清单和下载文件。真实网络恢复耗时仍取决于 Telegram 连接；本修复针对重复媒体读取及无阶段提示的问题。
